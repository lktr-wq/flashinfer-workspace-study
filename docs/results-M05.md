# S03-M05结果：容量边界处整批耗时缩短6.25%，单条延迟存在取舍

分析日期：2026-10-24。本轮4个独立进程、8个测试格、40次正式整批调用全部完成，证据有效，启动适配验收通过。

**在相同65%显存预算下，启动自动选择使更多缓存可用，四条16K长请求的整批中位耗时从13.669秒降到12.815秒，缩短0.854秒、6.25%。更高并发也使第1条请求生成完整回答的时间延后约2.20秒。**

本轮属于 **1到2**：沿用上游注意力算子、空间查询、范围估算以及vLLM原生调度，验证启动配置改进怎样转成真实模型生成的收益。改动位于工作区启动选择与框架接入。

## 1. 两档负载的完整生成结果

每次同时提交四条请求，每条固定生成128个token。四个进程按默认→自动→自动→默认运行，后一对进程交换负载顺序；每档预热2次、正式测量5次。

## 2. 新增缓存怎样产生作用

| 项目 | 默认 | 自动选择 |
| --- | ---: | ---: |
| 临时工作区 | 394MiB | 32MiB |
| 实际历史缓存 | 1701MiB | 2062.8125MiB |
| 历史token总容量 | 62,208 | 75,440 |
| 12K档最大总需求 | 49,664 | 49,664 |
| 16K档最大总需求 | 66,048 | 66,048 |

自动侧省出362MiB工作区，实际增加361.8125MiB历史缓存，多容纳13,232个token，容量增加21.27%。缓存按块分配，产生少量取整。

12K档两边容量充足；16K档的需求落在两种容量之间。逐请求原始时间戳给出了直接的入场记录：

- 默认侧10/10次，第4条请求首次进入计算都发生在前3条中一条完成后约0.127—0.194毫秒。
- 自动侧10/10次，第4条请求都在前3条任何一条完成前3.33—3.64秒进入计算。
- 第4条首次排队中位时间由8.947秒降到7.594秒，首token时间由11.788秒降到10.560秒。
- 原生日志可见默认`Running:3, Waiting:1`和自动`Running:4, Waiting:0`。日志是定时采样，逐请求时间戳提供更细的时序。

这形成了清楚的链条：**启动预留缩小→可用历史缓存增加→第4条提前进入计算→整批更早完成。** 本轮正式调用抢占计数全部为0。

表中单条时间取自引擎排队到最后token生成的原生单调时钟记录；完整整批时间另用调用端计时。

第4条更早进入，使更多请求共同使用执行资源。前面几条的完成时间随之变化，第1条延后约2.20秒；整批最后完成时间提前约0.85秒。评价这项配置时，应一起看整批完成时间、吞吐和各条请求延迟。

适合继续推进的场景是：**显存预算受限、并发长请求使缓存紧张、业务更看重整批完成速度或整体处理量。** 对较早完成的单条请求有严格延迟要求时，需根据实际服务目标选择并发与缓存配置。
