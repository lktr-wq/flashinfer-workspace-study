# 提案：启动时按支持范围选择 FlashInfer 工作区，将节省预算交给原生 KV 缓存

更新：2026-10-24。状态：本地维护者讨论稿，尚未外发。本轮整理文档与复现入口，沿用已保存的数据。

## 1. 需要解决的实际问题

同样的模型和显存预算，FlashInfer 预留的临时工作区越大，vLLM 能留给历史 K/V 缓存的空间就越少。部分小模型、受限并发配置的真实空间需求明显低于默认预留；在接近缓存容量边界的长请求中，回收这部分空间可以使更多请求同时入场。

建议在服务启动时，根据已确定的模型、后端和调度上限选择工作区大小，再交给 vLLM 原生显存分析与自动 KV 分配。生成阶段复用已分配的工作区，CUDA Graph 捕获完成后保持地址与大小稳定。

本地结果中，工作区从 394MiB 降到 32MiB，历史 token 容量由 62,208 增至 75,440；四条 16K 请求的整批耗时在两轮中分别减少 6.25% 和 5.38%。收益集中在“默认缓存放不下四条、调整后放得下”的服务负载。

## 3. 实测收益、成本与验收状态

环境为 RTX 4060 Laptop / SM89，Qwen2.5-1.5B-Instruct，BF16，vLLM 0.28.0，FlashInfer 0.6.16.post3 的隔离修复副本。两侧 GPU 显存预算同为 65%。

| 指标 | 默认工作区 | 自动工作区 | 结果 |
| --- | ---: | ---: | --- |
| 浮点工作区 | 394MiB | 32MiB | 少预留 362MiB |
| 实际 KV 缓存 | 1701MiB | 2062.8125MiB | 增加 361.8125MiB，包含缓存块取整 |
| 历史 token 容量 | 62,208 | 75,440 | 增加 21.27% |
| S03-M05：四条 16K 输入、各生成 128 token | 13.668875秒 | 12.814543秒 | 整批减少 6.25% |
| S03-M06：同一性能输入复测 | 13.577162秒 | 12.846201秒 | 整批减少 5.38%，约 0.731秒 |
| M06 第一条请求排队至末 token 中位 | 8.915071秒 | 11.153288秒 | 延后约 2.24秒 |
| M06 第四条请求排队中位 | 8.894309秒 | 7.619215秒 | 提前约 1.28秒 |
| M06 生命周期 allocated 峰值 | 5227.0249MiB | 5236.0249MiB | 增加约 9MiB |
| M06 生命周期 reserved 峰值 | 5338MiB | 5314MiB | 减少 24MiB |

每轮均交换后端配置执行顺序，两个配置各有 10 次正式性能样本；各轮分别报告。M06 两种执行顺序分别省时 5.392% 和 5.371%。全部正式性能批次的抢占计数为 0。原生时序表明，默认侧第四条在其他请求完成后入场，自动侧第四条在其他请求完成前数秒入场。

对较短的四条 12K 请求，M05 整批仅减少约 0.44%；两条 8K 请求在 M04 基本持平。这些结果支持以**实际缓存压力与服务目标**决定是否启用：提高整批完成速度，同时接受首批请求分摊更多 GPU 资源的延迟取舍。

M06 启动查询分别耗时 3.552秒、3.438秒。完整初始化时间默认 59.466／58.032秒，自动 59.472／58.355秒。查询内部时间与完整启动时间分别记录。工作区申请函数中的查询次数为 0，正式生成前后工作区地址及大小稳定。

正确性记录如下：

- 新增长文标准题包含三道独立题、四个位置场景及重复测量。默认与自动各为 4/16 正确；16 组配对回答的文本和 token 序列全部相同，默认答对的 4 次全部保留。
- 32 份标准题输出均正常遇结束符停止，所选 token 概率有限。第 4 位场景存在有限 logprob 微差，生成词序保持一致。
- 原六道题两侧结果保持：短题 3/3、长题 1/3。共同长文错误、输入及标准答案均保留。
- 原始综合验收 `passed=false`、`new_quality_passed=false` 保留，触发项是预先约定的全题答对条件。相对回答保持、缓存容量和压力性能指标分别报告。

完整结果见 [S03-M06 结果分析](results-M06.md)。

## 4. 当前原型的支持条件

下表区分代码中实际检查的条件与已完成实验的配置。复用时应同时满足二者；将来扩大支持范围时应单独补充验证。

| 维度 | 当前代码检查 | 已完成实验的取值或前提 |
| --- | --- | --- |
| 框架生命周期 | vLLM 精确版本 0.28.0，V1 Model Runner；启动计划复用关闭 | `VLLM_USE_V2_MODEL_RUNNER=0`、`VLLM_ENABLE_STARTUP_PLAN=0` |
| 硬件 | SM89；读取实际 SM 数量参与计算 | RTX 4060 Laptop，24 SM、8GB 显存 |
| 注意力层 | 所有 KV 层为原生 FLASHINFER，单一、均匀的 AttentionSpec 组 | Qwen2.5-1.5B 的普通因果全注意力 |
| 头数与维度 | 12 个 Q 头、2 个 KV 头、head_dim=128 | Qwen2.5-1.5B-Instruct |
| 类型 | Q、KV、输出均 BF16；prefill/decode 的 Q 类型一致 | KV 类型 `auto` 最终解析为 BF16 |
| 分页与并行 | page_size=16，TP=1、DCP=1、PP=1 | 单卡 |
| 切分 | 自动 split，prefill/decode split 设置一致，允许 split-KV | 原生普通 FA2 路径 |
| 功能组合 | batch invariant、sinks、滑动窗口、非零 logits cap、自定义非因果 mask、speculative 路径触发回退 | 关闭 prefix caching / cascade；外部 RoPE，FlashInfer pos encoding 为 NONE |
| KV 预算 | `kv_cache_memory_bytes=None`，采用原生自动 KV 分配 | `gpu_memory_utilization=0.65` |
| 服务上限 | 正整数、int32 索引范围，`max_num_seqs <= max_num_batched_tokens`；实际值进入范围计算 | max_num_seqs=4，max_num_batched_tokens=512，max_model_len=16512 |
| Graph | 使用读取到的 Graph 配置计算上界，正式 builder 签名逐项匹配 | FULL_DECODE_ONLY，捕获 batch size 1、4 |
| 源码与接口 | 校验冻结的 scheduler、allocator、绑定及 wrapper 源码哈希 | S02-D02 隔离修复副本及已保存的 PR5236 摘录 |

普通 FA2、外部 RoPE和关闭 cascade 是冻结实验的路线前提。当前配置提取对 `use_cascade` 写入固定 false，范围策略的 `resolved_backend` 默认按 fa2 解释；通用集成需要从实际 builder/dispatch 获取这些值，并核验对应路由。

范围计算覆盖的是调度上限内的请求行分布；当前工程收益已经在上表冻结服务配置中完成实测。32MiB 来自这套配置，扩大服务上限时应重新计算和验收。

## 5. 配置优先级：现代码与拟议接口

### 现代码的实际行为

当前研究开关为 `FI_STARTUP_WORKSPACE_MODE=default|auto`，默认 `default`。

| 配置情况 | 当前行为 |
| --- | --- |
| mode=default | 使用原生工作区申请流程 |
| mode=auto，读取到的工作区数值不等于 394MiB | 保留原生配置，记录 `explicit nondefault workspace configuration is preserved` |
| mode=auto，数值等于 394MiB，全部支持检查通过，推荐值更小 | 选择推荐值；本轮为 32MiB |
| mode=auto，数值等于 394MiB，检查失败或没有缩小空间 | 记录原因并使用原生流程 |
| mode 取其他值 | 立即报配置错误 |

**显式指定 394MiB 的识别存在待改项。** 当前代码仅比较读取后的数值，用户显式写入 394MiB 时也会进入自动选择；实验协议本身显式写入了该数值并配合 auto 授权。通用入口需要增加“配置是否由用户显式提供”的来源信息。

### 建议的正式优先级

1. 用户显式给出的工作区大小最高优先，包括恰好等于默认值的 394MiB；记录为 `manual`。
2. 用户选择自动模式且没有手动大小时，对实际后端和服务上限进行支持检查；检查通过后采用范围需求、余量和原生保护下限的最大值。
3. 自动模式遇到支持范围外的配置、接口缺失、校验不一致或收益为零时，保留框架原有分配并记录原因。
4. 默认兼容模式继续原生行为。自动模式的默认开关策略交由维护者决定。

建议使用框架原生配置枚举及配置来源标记。研究用 `FI_STARTUP_WORKSPACE_MODE` 可保留在复现包中，正式 API 命名由仓库维护者确定。

## 6. 回退与失败如何处理

### 现代码已经实现

启动选择阶段捕获异常，写入 `status=fallback` 和原因，继续调用原生 `determine_available_memory()`。支持范围不符、源码哈希失配、空间查询报错、查询超出范围上界、整数需求超过原 wrapper 的 8MiB、推荐值低于保护下限、推荐值无法缩小原预留等，均进入这条路径。

自动选择成功后，工作区 getter 对实际 builder 签名进行比较。签名改变时调用原 getter，并记录实际原生分配；同一 builder 已有工作区时直接复用。正式阶段 getter 内查询次数为零。

模式错误或启动计划复用开启时立即报错。实际工作区申请、原生显存分析、模型加载、Graph 捕获与生成阶段的错误向外报告。原型没有部署阶段的自动二次启动与预算重算流程。

### 正式集成建议

- 在确定 KV 预算与捕获 Graph 前完成支持检查、大小选择和持久工作区申请；采用原生生命周期钩子，替代当前类方法替换。
- 正式 builder 与启动选择条件发生变化时，先终止当前初始化并重走原生预算分析，随后重建 KV 与 Graph。将“回退后预算仍一致”纳入启动契约。
- 对范围查询返回支持标记、浮点/整数需求、对齐、版本/调度器标识、支持的功能组合和失败原因。框架保存决定和实际分配，便于报告问题。
- 查询只保留 CPU 数值与记录；临时 selector 和 wrapper 退出启动查询后释放。正式 arena、wrapper 与 Graph 按原生持久生命周期管理。
- 生成阶段固定已捕获的 arena；服务上限或后端发生改变时通过重新初始化选择空间。
- 保留请求失败、OOM 和 Graph 错误的原始日志；在明确完成预算重算的启动流程中启用默认回退。

## 7. 当前估算与选择规则

当前采用指定 FA2 scheduler 的范围上界，枚举 tile_q={16,32,64,128}，按服务行数、请求数、Q/KV 头数、SM 数量及 Graph padding 计算 FP32 partial output、softmax statistics 和 int32 metadata 的分配上界。

浮点空间选择规则为：

```text
原生保护下限 = max_num_batched_tokens × num_qo_heads × head_dim × 16
推荐空间 = 向上取整到MiB(max(32MiB, 范围浮点上界 × 9/8, 原生保护下限))
```

仅在推荐值小于当前原预留时采用。当前配置的范围浮点上界约 21.164MiB，最终选择 32MiB。14 次原生具体计划查询检查均未越过已计算上界。中间形状的覆盖依据是冻结调度器的范围公式，14 个查询作为启动交叉检查保存。

长期维护建议由 FlashInfer 提供与实际 scheduler 同源的范围接口，减少框架侧重复移植分配公式。若稳定接口尚未具备，提案可先明确支持路径和失败语义，由双方约定逐步接入方式。

## 8. 建议维护者先判断的事项

1. 范围空间需求接口是否适合由 FlashInfer 提供；与 PR5236 的已有设计如何衔接。
2. vLLM 是否采用在原生显存分析前确定 arena 的接入点；与持久工作区分析相关改动如何共用生命周期。
3. 是否接受先以普通 BF16 FA2、均匀注意力组和单卡为窄范围落地，其他配置沿用原生分配。
4. 自动与显式配置的优先级、支持检查失败后的行为、用户日志应使用怎样的原生配置契约。
5. 是否需要在同类容量边界负载上补充当前主分支复现，然后再扩展硬件或模型支持。

这些反馈决定后续补丁的放置位置和维护成本，适合作为正式扩大测试前的收敛关口。
